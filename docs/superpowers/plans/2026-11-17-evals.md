# Chat Evals Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `make eval MODEL=…` runs a fixed question set through the real Phoebe chat pipeline, grades each answer deterministically, and prints a per-model scorecard with a quality-first switching verdict.

**Architecture:** A `phoebe.evals` package: a YAML case schema, a grader over the chat `done` payload, a Bedrock ConverseStream answer model for candidates, a candidate/price table with a cost estimate, a scorecard with the verdict, and a runner that builds the in-process app (like `backend/scripts/live_chat_check.py`) with the chosen answer model injected into `Deps(answer=...)`. Each case logs in fresh. Results go to a git-ignored JSONL file.

**Tech Stack:** Python 3.14, FastAPI TestClient, pydantic, PyYAML (already a dependency), boto3 `bedrock-runtime` ConverseStream; pytest with stubbed clients (no AWS in tests).

**Spec:** `docs/superpowers/specs/2026-11-17-evals-design.md`

## Global Constraints

- Never touches staging or production: database must be `PHOEBE_LIVE_DATABASE_URL` whose name ends in `_live` (reuse `live_database_url()`); AWS us-east-2 only; owner's local credentials.
- No test calls AWS. Live runs are owner-only.
- Persona: Alex Rivera (Platform). Forbidden titles for "another team": `Sales Playbook`, `East Territory Notes`, `Payments Runbook`.
- Refusal codes from `backend/src/phoebe/chat/refusals.py`: `1001`, `1204`, `2307`, `3115`. A list question answered with `1204` is a failure.
- Candidate adapter: system = `backend/prompts/answer.txt` (via `ANSWER_PROMPT_PATH`), messages = what the app passes the answer model, `temperature` `0.1`, `maxTokens` = `PHOEBE_ANSWER_MAX_TOKENS`.
- Model names: `haiku` (production harness), `haiku-direct` (`us.anthropic.claude-haiku-4-5-20251001-v1:0` via the adapter), `kimi-k3.1` (`us.moonshotai.kimi-k3.1`), `glm-5.3` (`us.zai.glm-5.3`), `gpt-oss-120b` (`openai.gpt-oss-120b-1:0`), `all`.
- Switching rule (exact): a candidate qualifies only if, on the same run, (1) passes ≥ the cases `haiku` passes, (2) zero `must_not_cite` and zero `must_not_contain` hits across all cases and repeats, (3) flaky count ≤ Haiku's. Among qualifiers the cheapest estimated cost per answer wins; median latency breaks a tie. Otherwise the verdict is `keep Haiku 4.5`. `haiku-direct` is a control: reported, never a candidate.
- Repeats: with `REPEAT=n`, a case passes for a model only if all repeats pass; mixed = flaky (reported separately from failed).
- Cost guard: print calls and estimated cost before any AWS call; continue only on `y` (TTY) or `YES=1`; with no TTY and no `YES=1`, exit non-zero without calling AWS.
- Results: `backend/evals/results/<UTC timestamp>-<model>.jsonl`, flushed per line, git-ignored.
- Commit trailer: `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. A stream that ends in an `error` event or a non-200 (429, 503, `3115`): the case is recorded as `error` (a failure with the error code), and the run continues (Task 6 `test_run_case_records_error_event`).
2. A candidate that rejects the request shape (ValidationException, no system block or no streaming): that model is reported `unsupported` once, its cases skipped, and other models still run (Task 3 `test_validation_error_is_unsupported`, Task 6 `test_unsupported_model_is_skipped_not_fatal`).
3. Ctrl-C or a crash mid-run: every finished case is already a complete line in the results file (Task 6 `test_results_are_flushed_per_case`).
4. No TTY and no `YES=1`: exits non-zero before any model call (Task 4 `test_confirm_refuses_without_tty_or_yes`).
5. A follow-up whose first turn was refused: the follow-up still runs and is graded on its own expectations; the first turn's failure is reported against that turn (Task 6 `test_follow_up_runs_after_refused_first_turn`).
